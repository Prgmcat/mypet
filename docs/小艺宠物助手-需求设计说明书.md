## 0. 阅读指南与关键假设

### 0.1 本文档解决什么问题

本文档把产品目标与业务构想转化为可开发、可测试、可验收的需求基线，是项目后续设计、开发、测试、验收与运营的唯一需求依据；任何范围或规则变更均需通过本文档变更流程。文档覆盖：

- 产品定位、用户与场景、范围边界；
- 功能需求（含需求编号、优先级、业务规则、验收标准）；
- 数据模型、接口需求、Flutter 全平台客户端技术方案；
- 权限、隐私合规、非功能指标、埋点、里程碑与风险。

### 0.2 关键假设（需评审确认）

1. **客户端形态**：采用 **Flutter 全平台客户端**，一套代码覆盖 HarmonyOS NEXT / Android / iOS / Windows / macOS / Linux；移动端（含鸿蒙）为首发重点，PC 端共用同一套代码与 API、按 P1 交付。小艺生态（语音入口、服务卡片、意图框架）作为后续增强，不阻塞 MVP。
2. **服务端由项目自建**：账号、档案、同步、AI 编排、推送、对象存储、内容后台均按自建服务设计；AI 模型可选用盘古或合规第三方大模型，通过服务端统一编排，客户端不直连模型。
3. **AI 定位为科普与辅助**：不提供诊断、处方、具体用药剂量，不替代执业兽医；重症风险必须引导就医。
4. **"电子身份证"为平台内数字档案卡**：不是政府或行业官方证件，UI 与文案不得暗示官方认证。
5. **平台范围**：HarmonyOS NEXT / Android / iOS / Windows / macOS / Linux 统一客户端；手机、折叠屏、平板与 PC 共用一套 Flutter 代码与同一套 API。移动端为首发重点，PC 端按 P1 交付；允许按平台分阶段发布，但不拆分为多套客户端。手表、车机、Web、小程序不在本期（Web 可作为 P2 预留）。
6. **数据合规地域**：中国大陆，遵循《个人信息保护法》《数据安全法》《生成式人工智能服务管理暂行办法》，并同时满足华为应用市场、Google Play、Apple App Store 的审核要求。

## 1. 项目概述

### 1.1 背景

养宠家庭在宠物全生命周期中面临三类高频问题：

1. **信息碎片化**：疫苗本、病历、照片散落在纸质材料与手机相册，就医或寄养时无法快速调取。
2. **养护节点易遗漏**：驱虫、疫苗加强、体检、洗护周期依赖记忆，漏做会带来健康风险。
3. **建议不精准**：网络信息泛化，无法结合品种、年龄、疫苗史、既往病史给出个体化建议；新手难以判断异常是否需要就医。

### 1.2 产品定位

**一句话定位**：以宠物电子档案为数据底座、以 AI 问答为交互入口、以智能提醒为执行闭环的 Flutter 全平台养宠管理 App。

**核心价值主张**：

- **一宠一档**：每只宠物拥有独立、可持续更新的全生命周期档案。
- **档案驱动 AI**：AI 回答必须读取当前宠物档案上下文，拒绝通用模板。
- **自动闭环**：记录 → 计算下次节点 → 提醒 → 完成 → 写回记录。
- **可信边界**：AI 只做科普与分诊建议，重症明确引导就医。

### 1.3 产品目标与成功指标

| 层级 | 指标 | 首年目标（建议值，待评审） |
| --- | --- | --- |
| 北极星 | 周有效管理用户数（周内完成 ≥1 次记录或提醒） | 建立基线后季度环比 +15% |
| 激活 | 新用户 24h 内完成首只宠物建档率 | ≥ 60% |
| 档案 | 建档用户中档案完整度 ≥ 70% 的占比 | ≥ 45% |
| 留存 | 次日 / 7 日 / 30 日留存 | 45% / 28% / 15% |
| AI | 建档用户 7 日内使用 AI 问答渗透率 | ≥ 50% |
| 提醒 | 到期提醒的完成率 | ≥ 55% |
| 分享 | 创建过照顾任务的用户占比（P1 上线后） | ≥ 8% |
| 质量 | 崩溃率 / 卡死率 | < 0.1% / < 0.05% |

### 1.4 范围

**本期范围（P0 + P1）**

- 多端账号登录（鸿蒙华为账号 / iOS 与 macOS Apple 登录 / Android Google 登录 / PC 手机号或二维码登录 / 全平台手机号验证码）、多宠档案、电子身份证卡；
- 疫苗 / 驱虫 / 体检 / 病历 / 体重 / 相册等健康与成长记录；
- 档案驱动的 AI 文本问答、风险分级、会话历史；
- 自动提醒中心、本地通知与远程推送、通知栏快捷操作；
- 任务二维码分享与照顾者反馈（P1）；
- PC 端（Windows / macOS / Linux）响应式布局、文件导入导出、打印、桌面通知与快捷键（P1）；
- 养宠百科、首页聚合、设置与隐私合规。

**明确不做（本期）**

- 在线问诊、处方流转、药品售卖、保险、宠物交易；
- 社交社区、UGC 公开内容；
- 智能硬件接入（项圈、喂食器、摄像头）；
- 多语言、Web 独立端、小程序；
- 小艺深度集成（语音技能、意图框架）作为 P2；
- 官方证件、芯片登记、城市养犬登记对接。

### 1.5 术语

| 术语 | 说明 |
| --- | --- |
| 档案 / 电子身份证 | 平台内单只宠物的结构化数字档案与其展示卡 |

## 2. 用户与场景

### 2.1 用户画像

| 画像 | 特征 | 核心诉求 | 产品侧重 |
| --- | --- | --- | --- |
| 新手铲屎官 | 首次养宠，知识不足，易焦虑 | 知道"现在该做什么" | 建档引导、百科、AI 问答、提醒 |
| 忙碌上班族 / 经常出差 | 时间碎片化，依赖工具 | 不漏关键节点、可远程托管 | 自动提醒、任务分享、多端同步 |
| 多宠家庭 | 2 只及以上宠物 | 快速区分、分别管理 | 多宠切换、档案隔离、批量待办 |
| 科学养宠型 | 主动学习，关注数据 | 趋势、记录、可追溯 | 体重曲线、健康时间线、导出 |

### 2.2 核心痛点 → 需求映射

| 痛点 | 典型场景 | 对应需求 |
| --- | --- | --- |
| 纸质档案易丢、信息分散 | 就医时找不到疫苗批号 | PET、REC、电子证件分享 |
| 养护周期记不住 | 忘记体内驱虫已超 30 天 | REM 自动提醒 |
| 网上建议不针对自家宠物 | 同样"软便"，幼猫与老年猫建议不同 | AI 档案上下文 |
| 异常时不知道是否该就医 | 深夜呕吐，无法判断紧急程度 | AI 风险分级 + 就医提示 |
| 出差期间无人照护 | 需要朋友上门喂猫并反馈 | SHR 任务分享 |
| 换手机数据丢失 | 旧手机损坏 | SYN 云端同步 |

### 2.3 关键用户旅程

**旅程 A：新用户首次建档（目标 ≤ 3 分钟）**

1. 启动 → 隐私政策与用户协议 → 华为账号一键登录。
2. 首页空状态 → "为我的宠物建档"。
3. 填写：头像、名字、物种、品种、性别、生日、绝育状态、体重（必填 7 项，其余可跳过）。
4. 选择是否已有疫苗/驱虫记录 → 有则引导补录最近一次。
5. 生成电子身份证卡 → 进入首页，展示"档案完整度 60%，补充过敏史可提升建议准确度"。

**旅程 B：记录 → 提醒 → 完成闭环**

1. 用户在"健康记录"新增一条体内驱虫记录（日期、药品、剂量、体重）。
2. 系统按周期规则计算下次到期日，生成提醒实例。
3. 到期前 T-3、当天 T0 推送通知；用户点击"已完成"。
4. 快捷记录面板预填本次类型与日期 → 保存 → 自动计算下一次到期。

**旅程 C：AI 个性化问答**

1. 用户在对话页选择宠物"咪咪"（或直接提问，AI 识别宠物名）。
2. 输入"今天突然软便，精神还好，怎么办？"。
3. 客户端展示"正在结合咪咪的档案分析"。
4. 流式返回：先给风险分级与初步建议，再给观察要点与就医红线。
5. 若命中 L3 红旗症状，顶部固定展示紧急就医提示卡。
6. 用户可一键"记录本次症状"或"设置观察提醒"。

**旅程 D：出差任务分享（P1）**

1. 主人创建"咪咪的日常照顾"任务：喂食、换水、铲屎、拍照反馈。
2. 生成二维码/链接，设置 7 天有效、可选 4 位口令。
3. 照顾者扫码打开 H5，无需注册，查看任务与紧急联系人。
4. 逐项勾选、拍照提交；主人收到进度通知并可查看照片。
5. 任务结束自动归档，分享链接失效。

         └─ 百科（P1）：分类 → 详情 → 搜索

### 3.3 全局交互原则

- **一屏一事**：核心任务不超过 3 步；新建记录优先使用模板与默认值。
- **状态完整**：每个列表页必须具备加载、空、错误、离线四种状态。
- **可逆操作**：删除记录、撤销分享、退出登录等需二次确认；删除提供 30 天回收站（云端）。
- **渐进式授权**：权限在首次使用对应功能时申请，并说明用途；拒绝后提供降级路径。
- **AI 透明**：AI 生成内容有明确标识；回答中引用档案时展示"依据：咪咪的档案"。

## 4. 功能需求

### 4.1 账号与多宠（ACC）

#### 4.1.1 功能清单

| 编号 | 需求 | 优先级 | 验收要点 |
| --- | --- | --- | --- |
| ACC-001 | 平台账号一键登录 | P0 | 鸿蒙华为账号 / iOS 与 macOS Apple 登录 / Android Google 登录 / Windows、Linux 手机号或二维码登录；首次授权后 3 秒内完成；失败可重试并给出原因 |
| ACC-002 | 手机号验证码登录 / 绑定 | P0 | 60 秒倒计时、防刷、异常提示；用于非华为设备兜底 |
| ACC-003 | 登录态保持与静默续期 | P0 | 冷启动无需重复登录；Token 过期自动刷新 |
| ACC-004 | 多设备数据同步 | P0 | 同一账号两台设备，5 秒内看到对方新增记录（在线） |
| ACC-005 | 共同照护者授权（P1） | P1 | 可邀请家庭成员只读/可编辑；可随时撤销 |
| ACC-006 | 账号注销与数据删除 | P0 | 二次确认 + 15 天冷静期；到期删除并可出具删除结果 |
| ACC-007 | 第三方账号解绑 | P1 | 解绑前校验至少保留一种登录方式 |

#### 4.1.2 业务规则

- 一个账号可创建多只宠物，MVP 上限 20 只；超出提示联系客服。
- 宠物归属以 `ownerUserId` 为准；共同照护者通过授权关系访问，不转移归属。
- 未登录用户可浏览百科与隐私政策，不可建档、不可使用 AI 问答。
- 注销冷静期内再次登录可撤销注销；冷静期结束后不可恢复。
- 登录能力通过 `IAuth` 抽象隔离：鸿蒙使用华为账号，iOS 与 macOS 使用 Apple 登录（若提供任何第三方登录，必须同时提供 Apple 登录），Android 使用 Google 登录或手机号，Windows/Linux 使用手机号验证码或扫码登录；服务端统一映射为内部 `userId`，客户端不感知平台差异。
- 全平台账号体系互通：同一手机号或同一华为/Apple/Google 账号在服务端绑定后，档案与提醒保持一致；换端登录不丢失数据。

### 4.2 宠物电子身份证与档案（PET）

#### 4.2.1 功能清单

| 编号 | 需求 | 优先级 | 验收要点 |
| --- | --- | --- | --- |
| PET-001 | 新建宠物档案 | P0 | 必填项校验、头像上传、3 分钟内完成；重复点击不重复创建 |
| PET-002 | 编辑 / 归档 / 删除宠物 | P0 | 归档后不出现在首页但可恢复；删除进入 30 天回收站 |
| PET-003 | 多宠列表与快速切换 | P0 | 首页与问答页均可切换；当前宠物全局可见 |
| PET-004 | 年龄自动计算与生命阶段 | P0 | 按生日实时计算；跨月/跨年边界正确 |
| PET-005 | 品种库与自定义品种 | P0 | 犬/猫常见品种可搜索；支持"其他/混血" |
| PET-006 | 过敏史、慢性病、长期用药 | P0 | 多选 + 自由文本；AI 问答必须读取 |
| PET-007 | 电子身份证号生成 | P0 | 格式 `PET + 年份 + 6 位序列`，全局唯一、不可修改 |
| PET-008 | 电子身份证卡预览 | P0 | 展示头像、名字、品种、年龄、性别、绝育、证件号、二维码 |

#### 4.5.2 上下文组装（服务端）

客户端只传 `petId + sessionId + 用户消息 + 附件`，服务端组装：

```json
{
  "pet_profile": {
    "species": "cat",
    "breed": "美国短毛猫",
    "sex": "female",
    "age_months": 14,
    "neutered": true,
    "weight_kg": 3.2,
    "allergies": [],
    "chronic_conditions": [],
    "medications": []
  },
  "health_recent": [
    {"type": "deworming", "date": "2026-09-21", "product": "体内驱虫", "next_due": "2026-10-21"},
    {"type": "vaccine", "date": "2026-08-28", "name": "猫三联", "next_due": "2027-08-28"}
  ],
  "user_question": "今天突然软便，精神还好，怎么办？",
  "attachments": [{"type": "image", "object_key": "..."}]
}
```

**约束**

- 上下文仅包含与问题相关的最近 12 个月记录摘要，避免超长。
- 不向模型传递用户手机号、地址、证件号等身份信息。
- 模型输出经内容安全与医疗规则双重校验后再下发。
- Prompt 模板版本化，服务端可灰度与回滚。

#### 4.5.3 风险分级规则

| 级别 | 判定 | 展示 | 示例 |
| --- | --- | --- | --- |
| L0 | 日常科普、无异常描述 | 正常回答 | "猫咪每天喝多少水合适" |
| L1 | 轻微异常，可居家观察 | 观察要点 + 复诊条件 | 偶发软便、轻微掉毛 |
| L2 | 建议 24 小时内就医 | 黄色提示卡 + 就医建议 | 持续呕吐、精神沉郁、食欲下降 > 24h |
| L3 | 紧急就医 | 红色固定卡 + 急诊提示 | 呼吸困难、抽搐、大量出血、误食毒物、无法排尿、意识丧失、难产 |

**红线症状库（示例，需兽医顾问审定）**

- 呼吸：张口呼吸、呼吸急促、黏膜发绀；
- 神经：抽搐、共济失调、意识丧失；
- 消化：持续呕吐、呕血、便血、腹胀坚硬；
- 泌尿：频繁蹲猫砂盆但无尿、排尿困难；
- 中毒：误食巧克力、百合、老鼠药、人用药；
- 其他：高热、严重外伤、难产、休克。

**回答结构（建议）**

1. 一句话结论与风险级别；
2. 结合档案的个体化依据（年龄、疫苗、驱虫、病史）；
3. 居家可做的 2–4 条措施；
4. 必须就医的红线；
5. 免责声明与"记录本次症状"入口。

#### 4.5.4 验收标准（P0）

- [ ] 同一问题在两只不同宠物下提问，回答体现年龄/疫苗/驱虫差异。
- [ ] 提问未指定宠物且账号有多只宠物时，AI 先询问"是哪只宠物"，不猜测。
- [ ] 命中 L3 红旗词时，无论模型正文如何，页面顶部固定展示紧急就医卡。
- [ ] 回答中不出现具体处方药剂量；出现时被服务端规则拦截并改写。
- [ ] 断网或超时提示明确，可重试；重试不产生重复消息。
- [ ] 会话历史按宠物隔离，切换宠物不串会话。

#### 4.6.3 提醒生成与去重规则

1. 记录保存成功后，服务端按 `petId + type + recordId` 计算 `nextDueAt`。

3. 提醒实例使用 `occurrenceKey = ruleId + dueDate`，客户端与服务端按该键去重。
4. 用户完成提醒：
   - 生成一条对应类型的记录（日期默认今天，可编辑）；
   - 规则锚点更新为新记录；
   - 旧实例状态置为 `done`。
5. 用户跳过：实例置为 `skipped`，规则保留，下一次到期照常计算。
6. 用户关闭某类提醒：规则 `enabled=false`，不再生成实例，但历史实例保留。

#### 4.7.2 分享安全规则

- Token 使用 128 位随机数，服务端仅存哈希；默认 7 天有效，最长 30 天。
- 链接中的 Token 放在 URL fragment 或一次性短码中，避免进入访问日志与 Referer。
- 支持随时撤销；撤销后立即失效，已打开页面下次请求返回失效提示。
- 可选 4 位口令，连续 5 次错误锁定 10 分钟。
- 照顾者上传照片前移除 EXIF；单张 ≤ 10 MB，最多 9 张/任务项。
- 紧急联系人默认展示为 `138****8888`；主人显式开启后才展示完整号码。
- 接口限流：单 Token 60 次/分钟/IP；异常访问触发风控与告警。
- 任务页不展示宠物完整病历、过敏史等敏感档案，仅展示照护必需信息。

#### 4.7.3 任务状态机

```
created → shared → in_progress → submitted → completed
   │         │           │            │
   └─────────┴───────────┴────────────┴→ revoked / expired
```

- `completed`：所有必填项完成并提交。
- `expired`：超过 `expiresAt` 未完成，只读展示。
- `revoked`：主人主动撤销，立即不可访问。

#### 4.7.4 验收标准（P1）

- [ ] 未登录用户扫码可在 3 秒内打开任务页，页面不要求注册。
- [ ] 任务链接过期或撤销后，页面展示明确失效原因，不泄露任务内容。
- [ ] 照顾者只能看到任务项、宠物昵称/头像、注意事项、紧急联系人，看不到病历。
- [ ] 照片上传成功后主人 5 秒内收到推送并可查看。
- [ ] 同一任务项重复提交不会产生重复反馈记录。

## 5. 关键业务规则汇总

### 5.1 年龄与生命阶段

- 年龄 = 当前日期 − 生日；不足 1 岁显示"X 个月"，不足 1 个月显示"X 天"。
- 仅知估算年龄时，标记"约"，且不参与精确疫苗周期计算，需提示用户补全。
- 生命阶段（幼年/成年/老年）阈值由服务端配置，按物种与体型区分，客户端仅展示。

### 5.2 提醒优先级与冲突

- 同一天多条提醒：疫苗 > 驱虫 > 体检 > 洗护 > 生日。
- 同一时刻最多合并为一条系统通知（"今天有 3 项养护待办"），点击进入提醒中心。
- 免打扰时段内到期的提醒顺延至时段结束，不丢失。

### 5.3 AI 安全与内容规则

- 禁止输出：确诊结论、处方、具体药物剂量、人用药替代方案、安乐死建议。
- 必须输出：风险级别、就医红线、免责声明。
- 用户描述含自伤/他伤风险（罕见）时，转人工客服提示，不继续生成。
- 所有 AI 回答带"AI 生成，仅供参考"标识；用户可举报。

### 5.4 档案完整度计算（建议权重）

| 字段 | 权重 |
| --- | --- |
| 头像 | 5% |
| 名字 / 物种 / 品种 / 性别 / 生日 / 绝育 | 各 8%（合计 48%） |
| 当前体重 | 10% |
| 最近一次疫苗 | 12% |
| 最近一次驱虫 | 12% |
| 过敏史 / 慢性病 | 各 6.5%（合计 13%） |

完整度 ≥ 80% 展示"档案完善"，60–79% 展示补充建议，< 60% 展示引导卡。

### 5.5 删除与保留策略

| 数据 | 保留策略 |
| --- | --- |
| 宠物与关联记录 | 删除后 30 天回收站，到期物理删除 |
| 单条记录 | 删除后 30 天回收站 |
| AI 会话 | 默认保留 180 天，用户可手动删除 |
| 分享任务 | 结束后 30 天删除 |
| 账号 | 注销冷静期 15 天，到期删除；备份 90 天内轮转清除 |
| 操作日志 | 180 天 |

## 8. 接口需求

### 8.1 通用约定

- 基础路径 `/v1`，JSON over HTTPS；AI 流式使用 SSE。
- 鉴权：`Authorization: Bearer <accessToken>`；刷新 Token 单独接口。
- 请求头：`X-Request-Id`（客户端生成 UUID）、`X-Client-Version`、`X-Platform: harmony`。

- 统一响应：

  "message": "ok",

}

## 9. Flutter 全平台客户端技术方案

### 9.0 选型结论

- **唯一客户端技术栈**：Flutter + Dart，一套代码覆盖 HarmonyOS NEXT / Android / iOS / Windows / macOS / Linux，不维护多套 UI。
- **鸿蒙适配方式**：基于 OpenHarmony SIG 的 Flutter 适配版本，不是 Google 官方支持；必须锁定版本线，并在 M0.5 PoC 验证后再进入大规模开发。
- **PC 适配方式**：同一套 Widget + 统一响应式断点，新增桌面布局壳与平台通道；不复制页面与业务逻辑。
- **平台能力隔离**：账号、推送、定时提醒、扫码、PDF、分享、图片选择、文件选择、打印、窗口/托盘、安全存储全部通过 `lib/platform` 抽象 + 平台通道实现，业务层不直接依赖任何平台 SDK。
- **兜底策略**：若 PoC 发现某能力在鸿蒙端无可用插件，则该能力用 ArkTS 原生插件实现，Flutter 仅承载 UI 与业务；不因单点能力推翻整体技术栈。
- **发布策略**：全平台共用同一套 API 与领域模型，允许按平台分阶段发布；移动端（含鸿蒙）作为首发重点，PC 端按 P1 交付。

### 9.4 关键实现要点

**路由与深链**

- 使用 `go_router` 集中注册路由，路由表与页面参数强类型化。
- 深链统一为 `https://mypet.example.com/...`，各端分别配置 App Linking / App Links / Universal Links / 桌面 URI Scheme；自定义 Scheme `mypet://` 仅作兜底。
- 冷启动与热启动统一由 `DeepLinkService` 解析一次，避免重复跳转；未登录时先缓存目标路由，登录后恢复。

**状态与数据**

- 页面只依赖 Notifier 暴露的不可变状态；异步状态统一用 `AsyncValue` 表达加载/数据/错误。
- Repository 为唯一数据入口：先读本地库，再触发后台刷新；UI 不直接调用 Dio 或平台通道。
- 所有写操作走 `MutationQueue`，本地事务成功后立即更新 UI，再异步同步。

**同步与离线**

- 本地库为 cache-first 数据源；同步引擎基于 `cursor` 拉取增量。
- 写操作写入 `outbox` 表，按 `clientMutationId` 幂等提交；成功后更新本地 `version`。
- 冲突：服务端以 `version` 乐观锁；客户端收到 409 时拉取最新并做字段级合并，提示用户确认。
- 离线时读缓存、写排队；恢复网络后自动重放，失败项进入"待同步"列表可手动重试。

**AI 流式**

- `dio` 以 `ResponseType.stream` 发起请求，按 SSE 解析 `event` 与 `data`。
- 增量文本每 50–100 ms 批量刷新一次，避免逐字 `setState` 造成掉帧。
- 首字 8 s 超时；取消后保留已生成内容；重试使用同一 `clientMessageId` 幂等。
- 流式过程中禁止页面重建；消息气泡使用 `const` 子树与局部刷新。

**提醒与推送**

- 本地定时提醒通过平台通道注册到系统：鸿蒙 `reminderAgentManager`、Android 精确闹钟、iOS 本地通知；不依赖 App 常驻后台。
- PC 端：Windows 使用任务计划或应用内定时器，macOS 使用 `UNUserNotificationCenter`，Linux 使用应用内定时器 + libnotify；应用未运行时降级为下次启动补提醒。
- 远程推送由服务端按用户时区、免打扰时段与平台通道调度；各端推送 Token 统一上报到 `/v1/notifications/register`。
- 通知动作统一为 `complete / snooze / open`，由客户端路由到提醒详情或快捷完成面板。
- 客户端按 `occurrenceKey` 去重；同一提醒实例在多端只展示一次有效通知。

**图片、附件与 PDF**

- 图片选择优先使用系统 Picker，避免申请宽泛相册权限；拍照优先系统相机。
- 上传前统一压缩：长边 ≤ 1920 px、JPEG 质量 80、单图 ≤ 500 KB；EXIF（含 GPS）在客户端移除。
- 上传使用预签名 URL 直传对象存储；失败保留本地文件并支持重试。
- 证件卡使用 `RepaintBoundary` + `toImage` 生成图片，保证与 UI 一致。
- PDF 使用 `pdf` 包按 A4 版式生成，字段可勾选；导出后调用平台分享能力。

**账号与安全**

- `IAuth` 按平台实现：鸿蒙华为账号、iOS/macOS Apple 登录、Android Google 登录、Windows/Linux 手机号或扫码登录；手机号验证码作为全平台兜底。
- 服务端将各平台 OpenID 映射为内部 `userId`；同一手机号可绑定多个登录方式。
- Access Token 短时效（2 h），Refresh Token 长时效（30 天），存 `ISecureStorage`。
- 所有请求带 `X-Request-Id`、`X-Client-Version`、`X-Platform`；关键操作记录审计日志（服务端）。
- 证书校验开启；禁止在日志中输出 Token、手机号、分享 Token。

**PC 端适配**

- 响应式断点：宽度 < 600 单栏，600–1024 双栏，>1024 侧边导航 + 列表/详情双栏；使用同一套 Widget，不复制页面。
- 窗口：最小 960×640，记忆尺寸与位置；支持最大化、多显示器；"关闭到托盘"需用户显式开启，默认关闭即退出。
- 键盘与菜单：`Ctrl/Cmd+N` 新建记录、`Ctrl/Cmd+K` 搜索、`Ctrl/Cmd+S` 保存、`Esc` 关闭；提供应用菜单与右键菜单。
- 文件：使用 `file_selector` 打开/保存；支持拖拽图片/PDF 到记录或档案；批量导入按顺序处理并展示进度。
- 通知：使用系统通知（Windows Toast / macOS Notification Center / Linux libnotify）；无通知权限时降级为应用内消息中心。
- 打印：使用 `printing` 生成打印预览，支持健康记录、疫苗本与电子身份证卡。
- 更新：Windows/macOS 使用签名更新包并校验签名；Linux 通过包管理器或 AppImage 自更新；支持失败回滚。
- 性能：大窗口列表使用 Sliver + 分页；图片缓存设置上限；避免一次性加载全部相册。

**性能与包体**

- 首屏使用骨架屏 + 本地缓存；图片使用缩略图与 `cached_network_image` 等价能力。
- 长列表使用 `ListView.builder` / `SliverList`，避免一次性构建；图表只渲染可见区间。
- 使用 `--split-debug-info` 与符号表管理崩溃还原；Android 开启 R8，iOS 开启 bitcode 等价优化（按当前工具链）。
- 包体控制：按需引入字体与图标子集；大图与百科封面走 CDN；鸿蒙宿主工程与桌面打包避免重复携带 Flutter 引擎资源。
- PC 端启动优化：延迟初始化相机、打印、托盘等桌面能力；首屏只加载当前账号与宠物摘要。

### 9.6 错误与降级

| 场景 | 处理 |
| --- | --- |
| 无网络 | 顶部横幅；读缓存；写操作入队；AI 不可用并提示 |
| 401 | 自动刷新 Token；失败跳登录并保留页面栈 |
| 403 / 越权 | 提示无权限并返回列表；上报异常 |
| 409 冲突 | 拉取最新数据，字段级合并，提示用户确认 |
| 429 限流 | 展示倒计时，禁止连续点击 |
| 5xx | 统一错误页 + 重试；连续失败提示稍后再试 |
| AI 超时 | 保留已生成内容，展示"继续生成/重试" |
| 上传失败 | 保留本地文件，支持重试与删除 |
| PC 文件写入失败 | 提示路径与权限，允许另存为；不丢失编辑内容 |
| 平台能力不可用 | 例如鸿蒙插件缺失或 PC 无摄像头：隐藏入口或降级为文件导入/系统分享，不阻塞主流程 |

- **构建**：Android 使用 Gradle + AAB；iOS 使用 Xcode Archive；鸿蒙使用 DevEco / hvigor 构建宿主工程并嵌入 Flutter 产物；Windows 使用 MSIX/EXE；macOS 使用 Xcode + DMG；Linux 使用 AppImage + deb/rpm。
- **环境**：`dev / staging / prod` 三套环境通过 `--dart-define` 注入，禁止把密钥写入代码仓库。
- **签名与上架**：Android 使用 Play App Signing；iOS 使用 App Store Connect；鸿蒙使用 AGC 签名与华为应用市场；Windows/macOS 使用代码签名与公证；Linux 提供 SHA-256 校验。
- **自动更新**：Windows/macOS 使用签名更新包并校验版本与签名；Linux 通过包管理器或 AppImage 自更新；更新失败可回滚到上一版本。
- **质量门禁**：静态分析零 error、核心单元测试覆盖 ≥ 70%、Golden Test 通过、全平台冒烟通过。
- **灰度**：通过服务端 Feature Flag 控制功能开关；客户端版本按平台分阶段放量。
- **崩溃与性能**：各端分别接入崩溃符号化与启动/卡顿监控；按平台看板独立观测。
- **测试矩阵**：鸿蒙 NEXT 2 台（中端/高端）、Android 3 台（不同厂商/系统版本）、iOS 3 台（不同机型/系统版本）；Windows 2 台（Win10/Win11）、macOS 2 台（Intel/Apple Silicon）、Linux 2 台（Ubuntu/Fedora）；折叠屏与大字体各 1 台。

## 10. 权限与隐私合规

### 10.1 权限清单

| 能力 | HarmonyOS | Android | iOS | 申请时机 / 拒绝后降级 |
| --- | --- | --- | --- | --- |
| 网络 | `ohos.permission.INTERNET` | `INTERNET` | 无需声明 | 安装声明；不可用则主流程不可用 |
| 网络状态 | `GET_NETWORK_INFO` | `ACCESS_NETWORK_STATE` | 无需声明 | 仅影响离线提示与重试策略 |
| 通知 | 系统通知授权 | `POST_NOTIFICATIONS`（Android 13+） | 通知授权 | 首次创建提醒；拒绝则应用内红点 + 横幅 |
| 精确提醒 | `reminderAgentManager`（系统代理） | `SCHEDULE_EXACT_ALARM`（按商店政策申请） | 本地通知无需额外权限 | 首次创建提醒；Android 未获批则降级为非精确闹钟 + 应用内提醒 |
| 相机 | 系统 CameraPicker（通常无需权限） | `CAMERA` 或系统相机 | `NSCameraUsageDescription` | 首次拍照；拒绝则仅从相册选择 |
| 相册 | 系统 PhotoPicker（通常无需权限） | `READ_MEDIA_IMAGES` 或系统 Photo Picker | `NSPhotoLibraryUsageDescription`；PHPicker 无需授权 | 首次选择；拒绝则仅拍照 |
| 保存图片 | SaveButton 安全控件 | MediaStore（分区存储） | `NSPhotoLibraryAddUsageDescription` | 首次保存；拒绝则改为分享到其他应用 |
| 扫码 | Scan Kit 系统 UI（通常无需相机权限） | `CAMERA` | `NSCameraUsageDescription` | 首次扫码；拒绝则支持手动输入短码 |
| 震动反馈 | `VIBRATE` | `VIBRATE` | 无需声明 | 通知与操作反馈 |
| 推送 | HMS Push（无额外权限） | 通知权限 + 厂商通道 | 推送授权 | 首次开启提醒；拒绝则仅保留本地提醒 |

> 原则：优先使用系统 Picker、系统相机与安全控件，避免申请宽泛的相册/文件权限；所有权限在首次使用对应功能时申请，并说明用途与拒绝后的降级路径。

**PC 端授权**

| 平台 | 需要用户授权的能力 | 说明 / 降级 |
| --- | --- | --- |
| Windows | 通知（系统设置）、摄像头（系统隐私设置） | 文件选择无需全局权限；无摄像头则改为文件导入 |
| macOS | 通知、相机、照片、文件访问（沙盒） | 需在 Info.plist 声明用途并完成签名与公证；拒绝则文件导入/应用内消息 |
| Linux | 通知（桌面环境）、摄像头（PipeWire/V4L2） | Flatpak/Snap 沙盒需声明对应权限；无通知则应用内消息 |

> PC 端默认不扫描全盘、不申请全局文件系统权限；所有文件读写均由用户通过文件选择器或拖拽显式触发。

### 10.2 隐私合规要点

- 首次启动展示隐私政策与用户协议，用户同意后才初始化网络与统计 SDK。
- 提供《个人信息收集清单》《第三方 SDK 清单》《数据导出与删除说明》。
- 收集手机号需单独说明用途；AI 问答上传的图片需说明将用于识别与档案记录。
- 个性化推荐（P2）需单独同意，并提供关闭入口。
- 账号注销 15 天冷静期，到期删除；提供删除结果查询。
- 日志与埋点不采集明文手机号、Token、精确位置、通讯录。
- 图片上传前移除 EXIF（含 GPS）；分享链接默认脱敏。
- 生成式 AI：回答标注"AI 生成"，提供举报入口，建立内容安全审核与应急下线机制。
- 医疗内容：显著展示免责声明；不宣称诊断、治愈；医疗科普内容经兽医顾问审核。
- 账号删除：Apple App Store 与 Google Play 均要求在 App 内提供账号删除入口，ACC-006 必须随首发上线，不能只提供网页或邮件入口。
- 各端分别准备隐私政策 URL、权限说明、AI 功能说明、医疗类内容说明、测试账号；并填写 Apple Privacy Nutrition Label、Google Play Data Safety、华为应用市场隐私标签；如上架 Microsoft Store，补充对应隐私声明。
- 第三方 SDK 按平台分别列清单（推送、统计、崩溃、对象存储、AI 服务），用户同意隐私政策前不初始化。
- PC 端本地缓存、日志与导出文件写入系统应用数据目录；用户可在设置中清除本地数据；导出文件必须由用户显式选择保存路径。
- PC 端发布包需完成 Windows 代码签名、macOS 签名与公证、Linux 包校验；安装包内附隐私政策与卸载说明。
- 本期默认仅在中国大陆发行；如后续出海，需单独评估 GDPR / CCPA、数据出境与模型服务地域，不直接复用国内配置。

### 10.3 数据安全分级（建议）

| 级别 | 数据 | 措施 |
| --- | --- | --- |
| L1 公开 | 百科文章 | 可公开访问 |
| L2 内部 | 宠物昵称、品种 | 登录鉴权、传输加密 |

## 13. 风险与待确认事项

### 13.1 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| AI 幻觉或医疗建议越界 | 合规与信任风险 | 风险分级、红线词库、输出审核、兽医顾问、免责声明、人工兜底 |
| 用户录入负担高，建档流失 | 激活与留存下降 | 必填最小化、模板、扫码/OCR、稍后补全、完整度激励 |
| 推送到达率受系统限制 | 提醒失效 | 各端本地提醒 + 推送双通道；应用内红点；引导开启通知；国内 Android 接厂商通道；PC 端用应用内消息兜底 |
| 多端同步冲突 | 数据错乱 | 版本号 + 字段级合并 + 冲突提示 |
| 分享链接泄露 | 隐私风险 | 短时效 Token、口令、撤销、脱敏、限流、审计 |
| 小艺集成能力不确定 | P2 延期 | 本期解耦，按标准深链/意图能力预埋 |
| Flutter 鸿蒙适配滞后或插件缺失 | 鸿蒙端功能延期、体验下降 | M0.5 PoC 先验证；关键能力用平台通道自研；锁定适配版本；保留原生兜底 |
| 各端提醒/推送机制差异 | 提醒不触发、重复或延迟 | 统一 `occurrenceKey` 与通知动作协议；全平台设备矩阵逐项验收 |
| 多应用市场合规差异 | 上架延误 | 分市场清单、隐私标签、账号删除入口、AI 内容标识前置 |
| Flutter 包体与启动性能 | 首屏慢、下载转化低 | 延迟初始化、按需加载、包体预算、性能门禁 |
| PC 端能力差异（通知/相机/分享） | 功能缺失或体验不一致 | 文件导入、应用内消息、复制链接等降级；按 9.3 能力矩阵逐项验收 |
| 桌面打包、签名与自动更新 | 安装失败、更新不可用 | 三平台签名/公证前置；更新包签名校验与回滚演练 |
| 响应式适配成本 | 移动端体验被拖累 | 断点与组件规范先行；PC 端 P1 独立验收 |
| 图片存储成本 | 成本上升 | 压缩、缩略图、生命周期策略、冷存储 |

### 13.2 待确认问题

1. 移动端与 PC 是否同期发布？还是移动端先发、PC 跟随？与"小艺"的入口关系如何定义？

6. 是否收费？会员权益（如无限 AI 次数、云存储扩容）如何设计？

10. 各端最低系统版本、基准机型、最小内存与屏幕尺寸范围？
11. Flutter 鸿蒙适配采用社区方案还是团队自研维护？关键插件（推送、提醒、扫码、PDF、安全存储）的自研投入是否已计入排期？
12. PC 端分发渠道如何组合：官网直装、Microsoft Store、Mac App Store、Linux 包管理器分别覆盖哪些？
13. PC 端是否需要多窗口、托盘常驻、开机自启、系统级全局快捷键？
14. 是否将 Web 端纳入后续规划？采用 Flutter Web 还是独立 H5？
